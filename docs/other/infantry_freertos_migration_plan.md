#  全向轮步兵迁移方案（裸机 Demo -> Src/FreeRTOS 框架）

## 1. 背景与目标

当前已有一套跑通的裸机 `test/infantry_omni_demo`。迁移目标是：

1. 以 `Src` 的正式 FreeRTOS 架构为主线承载逻辑。
2. 单板（`ONE_BOARD`）优先，双板仅保留接口，不在本阶段落地。
3. 所有 CAN ID 和控制接口以已跑通 Demo 为基准。
4. 强化 `robot_def.h` 的“配置层”职责，统一参数与通用逻辑入口。
5. 将 `robot_cmd` 的不同控制链路（DT7/ET08/图传）做成可拆分、可移植的独立实现。

## 2. 迁移原则

1. **先等价迁移，再做增强**：先保证行为与 Demo 一致，再做结构优化。
2. **配置集中化**：ID、方向、PID、死区、映射系数全部集中在配置层管理。
3. **控制源插件化**：`robot_cmd` 只负责编排，不直接耦合具体遥控协议细节。
4. **接口前置**：即使当前只做单板，也保留双板扩展接口（CANComm 等）。
5. **保守调度**：先使用保守频率，确保总线与任务稳定，再提频。

## 3. 基线约束（必须遵守）

### 3.1 CAN 与 ID 基线（来自 `test/infantry_omni_demo`）

1. CAN1：底盘 M3508 `id1/2/3/4` + yaw GM6020 `id1`
2. CAN2：摩擦轮 M3508 `id1/2` + pitch GM6020 `id1` + 拨盘 M2006 `id6`

备注：DJI 驱动中 M2006/M3508 与 GM6020 的反馈 ID 计算不同，允许“同数字 ID”共存，但必须按电机类型正确注册。

### 3.2 本阶段边界

1. 只做全向轮步兵单板链路。
2. 不引入 wheelleg 平衡控制实现。
3. 双板适配只保留编译与接口扩展点，不做联调闭环。

## 4. 目标架构（迁移后）

## 4.1 配置层（`robot_def.h` 为核心）

`robot_def.h` 从“散落宏”提升为“配置中心”，至少统一：

1. 机器人选择与板型选择（one/chassis/gimbal）。
2. 全部 CAN 与 motor id 映射。
3. 控制源选择宏（DT7/ET08/图传）。
4. 控制参数（死区、比例、限幅、单发/连发参数、pitch hold/前馈参数）。
5. 任务频率建议值（用于后续和 `robot_task` 对齐）。

建议新增分组宏或配置结构（仍可先保持宏），避免参数散落在 `cmd/chassis/gimbal/shoot`。

## 4.2 `robot_cmd` 插件化

在 `Src/application/cmd/` 下拆分控制源目录：

1. `cmd/input_dt7/`
2. `cmd/input_et08/`
3. `cmd/input_datalink/`（先留接口，后实现）

`robot_cmd` 仅做三件事：

1. 拉取各 app 反馈；
2. 调用当前启用的输入后端产出统一控制命令；
3. 执行安全仲裁（急停/离线降级）并发布消息。

统一输入后端接口建议：

1. `Init`
2. `Update`
3. `IsOnline`
4. `FillCmd`（填充 `Chassis/Gimbal/Shoot_Ctrl_Cmd_s`）

## 5. 分阶段迁移步骤与期望结果

## 阶段 A：基线冻结与参数归档

步骤：

1. 从 `test/infantry_omni_demo` 抽取全部有效参数（ID、方向、比例、死区、射击状态机参数）。
2. 写入 `robot_def.h` 配置分组。
3. 建立“参数追踪表”（参数名、来源、当前值、调参建议）。

期望结果：

1. 参数有唯一真源，不再散落在多个 app。
2. 迁移过程中的行为偏差可快速定位为“参数问题”还是“逻辑问题”。

## 阶段 B：`robot_cmd` 输入后端解耦

步骤：

1. 将当前 `robot_cmd.c` 中 ET08 细节提取到 `cmd/input_et08/`。
2. 从原框架 `temp/.../robot_cmd.c` 抽离 DT7/键鼠逻辑到 `cmd/input_dt7/`。
3. 设计 `input_datalink` 的占位接口（未实现先返回无效输入）。
4. `robot_cmd` 根据宏选择后端，并支持保留多后端源码并行存在。

期望结果：

1. `robot_cmd` 主文件规模显著收敛，职责变成“调度 + 安全 + 发布”。
2. 新增控制链路不需要改 `chassis/gimbal/shoot`。

## 阶段 C：按 Demo 基线对齐各应用 ID 与控制行为

步骤：

1. 对齐 `chassis/gimbal/shoot` 的电机 ID 到 Demo 基线。
2. 对齐射击核心状态机（单发触发、连发、去抖、停止条件）。
3. 对齐云台关键行为（无跟随补偿、pitch 手动/保持、必要前馈）。

期望结果：

1. FreeRTOS 版本在操作手感和功能上接近裸机 Demo。
2. “能跑”变成“可复现可调”。

## 阶段 D：单板稳定性收口

步骤：

1. 完成单板全链路联调（遥控输入 -> cmd -> app -> 电机反馈）。
2. 加入离线降级策略（输入离线、关键反馈缺失、急停恢复）。
3. 输出最小可用调参清单（底盘/云台/发射分组）。

期望结果：

1. 单板稳定运行，具备比赛前调参与复现能力。
2. 为后续双板迁移留下明确接口（不重写业务逻辑）。

## 阶段 E：双板接口预留（本阶段只做预留）

步骤：

1. `#ifdef` 保留 `CANComm` 的收发结构与 topic 对应关系。
2. 在文档中标注双板时 cmd/chassis 的消息流与 ID 规划。

期望结果：

1. 后续双板迁移只需替换消息传输通道，不改控制核心。

## 6. 任务频率建议（本阶段）

1. INS：1kHz（保持）
2. Motor：先保守 500Hz 或维持现状后观测（总线压力高时优先降）
3. Robot Core：200Hz
4. Daemon：100Hz
5. UI：按通信稳定性调节

原则：先稳定再提频，避免迁移期把“控制逻辑问题”和“调度/总线负载问题”混在一起。

## 7. 验收标准（迁移完成判据）

1. 单板全链路稳定运行，无随机停机。
2. 遥控输入后端可切换（至少 ET08 与 DT7 可编译共存）。
3. CAN/ID 与 Demo 基线一致，收发无冲突。
4. `robot_def` 成为参数唯一入口，调参不再跨文件散改。
5. 输出迁移文档与参数文档，支持后续双板扩展。

## 8. 风险与规避

1. **ID 迁移冲突风险**：先做 ID 表核对，再批量替换。
2. **行为偏差风险**：先迁移状态机，再迁移优化项（前馈/滤波）。
3. **总线负载风险**：先保守任务频率，必要时降 Motor 频率。
4. **耦合回潮风险**：严格限制输入协议代码进入 `robot_cmd` 主文件。
